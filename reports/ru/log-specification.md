Это спецификация поддержанных форматов Client.txt и кодов нашего анализатора,
а не официальный исчерпывающий справочник внутренних кодов Path of Exile.
Неподдержанные строки сохраняются как unknown/error. Каталог ниже построен
из правил версии приложения, создающего отчёт; старый анализ не пересчитывается.

## Формат строки

Чтение бинарное, разделитель — LF. CRLF сохраняется отдельно; одиночный CR
не разделяет строки. Последний непустой фрагмент без LF также учитывается.
Текст декодируется строго как UTF-8, без глобального удаления пробелов.

Обычный заголовок:

```text
YYYY/MM/DD HH:MM:SS tick source [LEVEL Client PID] message
```

`tick` и `PID` — десятичные числа, `source` — шестнадцатеричное поле.
Уровни: `INFO`, `DEBUG`, `WARN`, `CRIT`, `ERROR`. Смысл `tick` и `source`
не установлен. Время интерпретируется в выбранной зоне IANA; неверная дата,
неоднозначное или несуществующее время дают ошибку, без угадывания смещения.

## Статусы и коды

| Статус | Значение |
| --- | --- |
| `recognized` | Полностью совпало конкретное правило формы сообщения |
| `unknown` | Форма не поддержана; байты и причина сохранены |
| `error` | Ошибка декодирования или временной отметки |

Сообщение об ошибке игры может иметь статус recognized: это не означает,
что описанная операция завершилась успешно. `type` — тип строки;
`rule_id` — применённый классификатор. Для сообщений они совпадают,
у диагностики и продолжений могут различаться.

## Поля построчного реестра

| Поле | Тип и смысл |
| --- | --- |
| `line_number` | Целое: номер физической строки с единицы |
| `byte_start`, `byte_end` | Целые: диапазон байтов `[start, end)` с разделителем |
| `raw_base64` | Строка Base64: точные байты, включая LF/CRLF |
| `line_ending` | `LF`, `CRLF` или `none` |
| `text` | UTF-8 без разделителя; отсутствует при ошибке декодирования |
| `status`, `type`, `rule_id`, `rule_version` | Строки: классификация и версия правил |
| `record_id` | Номер родительской строки или null |
| `fields` | Именованные поля правила: строки либо null для необязательной группы |
| `reason` | Причина unknown/error; null при recognized |
| `timestamp_raw` | Исходная отметка, если найден заголовок |
| `timestamp` | ISO 8601 со смещением при успешном преобразовании времени |
| `header` | Объект с `tick`, `source`, `level`, `pid` обычного заголовка |

Все физические строки учитываются ровно один раз. Диапазоны байтов должны
покрывать файл без пропусков и пересечений. Полный учёт и полное распознавание
различаются: последнее требует отсутствия unknown/error.

## Применение правил

Шаблоны сообщений проверяются через `fullmatch` после отделения заголовка.
Меньший приоритет проверяется раньше; первое совпадение определяет тип.
Поля сохраняются буквально. В раскрываемых блоках приведены точные регулярные
выражения Python: `\t`, `\r` и экранированные символы значимы.

Продолжения допустимы непосредственно после своего родителя и в указанном
порядке. Их тип — `<родитель>.field`, код правила — `<родитель>.<поле>`.
Пустая, ошибочная или неожиданная строка разрывает ожидание; собственного
времени у продолжения нет. Обрезанная последовательность в конце файла
пока не порождает отдельную ошибку отсутствующих строк.

## Границы толкования

Числовые `action_id`, `skill_type_id`, `object_id`, `flags`, `event_id`,
идентификаторы экземпляров и другие динамические значения не имеют здесь
выдуманного списка значений. Их допустимая форма видна в шаблоне; игровой
смысл может оставаться неизвестным. Идентификаторы областей, предметов и
пассивов — значения полей, а не коды правил. Сопоставление с RePoE является
отдельным исследованием и не заменяет подтверждённый смысл строки.

Конечные перечни ниже взяты из действующего каталога. Подписи реплик
не доказывают роль NPC; префиксы карт/арен применяются только аналитикой.
Пользовательские сообщения, переписка и сырые строки в справочник не включаются.
